# Documentación de código — Internacionalización (i18n)

Módulos: `core/i18n/`, `core/ports/translation_port.py`, `adapters/translations/json_translation_adapter.py`, `adapters/api/error_codes.py`, `adapters/api/routes/catalog.py`, cambios en `adapters/api/dependencies.py` y `adapters/api/main.py`, cambios en `core/exceptions.py`.

Feature spec de referencia: [`docs/specs/i18n-backend.md`](../../docs/specs/i18n-backend.md)

---

## Resumen de la feature

La feature i18n-backend añade al backend la capacidad de servir nombres de edificios, nombres de tropas y mensajes de error en el idioma del cliente (controlado por la cabecera `Accept-Language`). El catálogo de traducciones son archivos JSON versionados en git dentro del propio core del dominio.

---

## Módulos del core

### `core/i18n/__init__.py`

Archivo vacío. Declara el paquete `core.i18n`. No contiene lógica.

**Por qué existe**: Python requiere `__init__.py` para tratar el directorio como paquete importable.

---

### `core/i18n/languages.py`

**Qué hace**: define dos constantes:

```python
SUPPORTED_LANGUAGES: frozenset[str] = frozenset({"es", "en", "de", "fr", "ru"})
DEFAULT_LANGUAGE: str = "es"
```

`SUPPORTED_LANGUAGES` es un `frozenset` (inmutable, hashable, búsqueda O(1)).

**Por qué existe**: antes de esta feature, `SUPPORTED_LANGUAGES` estaba definido directamente en `adapters/api/dependencies.py`. El problema es que el adaptador de traducciones (`JsonTranslationAdapter`) también necesita saber cuáles son los idiomas soportados para el fallback. Definirlo en `adapters/` hubiera creado una dependencia de la capa de adaptadores hacia sí misma, violando la arquitectura hexagonal. Al moverlo a `core/i18n/`, se convierte en conocimiento del dominio y cualquier capa puede importarlo sin crear acoplamientos ilegítimos.

**Impacto en negocio**: es la fuente de verdad única para añadir o eliminar idiomas soportados. Cambiar este fichero afecta simultáneamente a la validación HTTP de la API y al comportamiento de fallback del catálogo.

---

### `core/ports/translation_port.py` — `TranslationPort`

Puerto (interfaz abstracta) que define el contrato que debe cumplir cualquier implementación de traducciones. El core nunca importa `JsonTranslationAdapter`; solo importa `TranslationPort`.

**Por qué existe**: la arquitectura hexagonal exige que el core no dependa de detalles de implementación (archivos, bases de datos). El puerto invierte la dependencia: el adaptador depende del core, no al revés. Si mañana las traducciones se sirven desde una BD o una API externa, solo cambia el adaptador; el core no se toca.

**Métodos** (ver referencia completa en [`referencia-funciones/translation-port.md`](referencia-funciones/translation-port.md)):

| Método | Retorno | Lanza excepción |
|---|---|---|
| `get_building_name(gid, lang)` | `str` | Nunca |
| `get_all_buildings(lang)` | `list[dict]` | Nunca |
| `get_troop_name(tribe, ordinal, lang)` | `str` | `TroopNotFoundError` si ordinal no existe |
| `get_troop_names_by_tribe(tribe, lang)` | `list[dict]` | `TroopNotFoundError` si tribu sin entradas |
| `get_message(code, lang, **params)` | `str` | Nunca |

**Impacto en negocio**: separa el CONTRATO (qué se puede pedir al sistema de traducciones) de la IMPLEMENTACIÓN (cómo se carga el catálogo). Permite testear el core sin archivos JSON reales.

---

### `core/exceptions.py` — Cambios aditivos (feature i18n)

**Qué cambió**: las 10 excepciones concretas existentes y 2 nuevas se migraron al patrón `error_code + params`.

Cada subclase concreta de `TravianBotError` declara ahora:
- `error_code: str` — constante en formato `SCREAMING_SNAKE_CASE`, usada para lookup en el catálogo de mensajes y para mapear al HTTP status code.
- `params: dict` — diccionario con los valores a interpolar en la plantilla de mensaje.

El método `str(exc)` (mensaje en español) se conserva intacto para compatibilidad con tests anteriores. El atributo `error_code` es estrictamente aditivo.

**Excepciones y sus códigos**:

| Clase | `error_code` | `params` | HTTP status |
|---|---|---|---|
| `AccountNotFoundError` | `ACCOUNT_NOT_FOUND` | `{"account_id": int}` | 404 |
| `DuplicateAccountError` | `DUPLICATE_ACCOUNT` | `{"username": str}` | 409 |
| `WorldNotFoundError` | `WORLD_NOT_FOUND` | `{"world_id": int}` | 404 |
| `SessionNotActiveError` | `SESSION_NOT_ACTIVE` | `{}` | 409 |
| `InvalidCredentialsError` | `INVALID_CREDENTIALS` | `{"username": str}` | 401 |
| `VillageNotFoundError` | `VILLAGE_NOT_FOUND` | `{"village_id": int}` | 404 |
| `FarmListNotFoundError` | `FARM_LIST_NOT_FOUND` | `{"farm_list_id": int}` | 404 |
| `LoginError` | `LOGIN_ERROR` | `{}` | 500 |
| `BrowserError` | `BROWSER_ERROR` | `{}` | 500 |
| `DatabaseError` | `DATABASE_ERROR` | `{}` | 500 |
| `TroopNotFoundError` | `TROOP_NOT_FOUND` | `{"tribe": str, "ordinal": str}` | 404 |
| `BuildingNotFoundError` | `BUILDING_NOT_FOUND` | `{"gid": int}` | 404 |

`TroopNotFoundError` y `BuildingNotFoundError` son las dos excepciones nuevas añadidas en esta feature.

**Nota sobre `TroopNotFoundError`**: cuando se lanza por tribu sin tropas en el catálogo (no por ordinal inexistente), el argumento `ordinal` puede ser `None`. El `params["ordinal"]` se serializa como `str(None or "")` = `""`.

**Impacto en negocio**: permite que cualquier excepción del dominio llegue al cliente en su idioma sin que el core tenga conocimiento de idiomas. La capa API es la única responsable de la traducción.

## Módulos del adaptador de traducciones

### `adapters/translations/json_translation_adapter.py` — `JsonTranslationAdapter`

**Qué hace**: implementación concreta de `TranslationPort` que lee catálogos JSON en memoria al inicio. Divide la carga en dos niveles: base (datos oficiales de Travian) y override (ajustes puntuales).

**Estructura interna**: tras el `__init__`, el adaptador mantiene tres `dict` en memoria:
- `self._buildings: dict[str, dict]` — clave: `str(gid)`, valor: dict con campos `alias`, `es`, `en`, `de`, `fr`, `ru`.
- `self._troops: dict[str, dict]` — clave: `"TRIBE_ordinal"` (ej. `"ROMANS_1"`), valor: dict con campos de idioma.
- `self._messages: dict[str, dict]` — clave: `error_code`, valor: dict con plantillas por idioma.

El merge override sobre base es un `{**base, **override}` de nivel superior: si la misma clave existe en ambos, el valor completo del override reemplaza al del base (no es un merge profundo campo a campo).

**Comportamiento en startup**:
- Archivos base (`buildings.json`, `troops.json`, `messages.json`): **obligatorios**. Si falta alguno o está corrompido, se lanza `RuntimeError` y la app no arranca.
- Archivos override: **opcionales**. Si no existen, se ignoran silenciosamente. Si existen pero son JSON inválido, sí se lanza `RuntimeError`.

**Lógica de fallback granular**: para cualquier texto (edificio, tropa o mensaje), si el idioma pedido tiene la clave pero el valor es una cadena vacía o ausente, se usa el valor en `es`. El fallback es entrada a entrada, no catálogo completo. Ver detalles en [`referencia-funciones/translation-port.md`](referencia-funciones/translation-port.md).

**Por qué existe**: desacopla el mecanismo de almacenamiento (JSON en git) del contrato del dominio (`TranslationPort`). El catálogo de Travian es estático y pequeño (~40 edificios, ~50 tropas totales); cargar todo en memoria al startup es la solución correcta: sin I/O en runtime, sin concurrencia compleja, sin infraestructura adicional.

**Impacto en negocio**: garantiza que la API no haga I/O durante las consultas de catálogo. Las respuestas son O(1) en términos de acceso a disco. El `Cache-Control: public, max-age=3600` que el middleware añade es coherente con esto: el cliente también puede cachear.

## Módulos de la capa API

### `adapters/api/error_codes.py`

**Qué hace**: define el mapa `ERROR_HTTP_MAP: dict[str, int]` que asocia cada `error_code` de dominio a su HTTP status code.

```python
ERROR_HTTP_MAP = {
    "ACCOUNT_NOT_FOUND":   404,
    "DUPLICATE_ACCOUNT":   409,
    "WORLD_NOT_FOUND":     404,
    "SESSION_NOT_ACTIVE":  409,
    "INVALID_CREDENTIALS": 401,
    "VILLAGE_NOT_FOUND":   404,
    "FARM_LIST_NOT_FOUND": 404,
    "TROOP_NOT_FOUND":     404,
    "BUILDING_NOT_FOUND":  404,
    "LOGIN_ERROR":         500,
    "BROWSER_ERROR":       500,
    "DATABASE_ERROR":      500,
}
DEFAULT_ERROR_STATUS: int = 500
```

**Por qué existe**: el mapeo de error semántico a HTTP status es responsabilidad de la capa de transporte (HTTP), no del dominio. El dominio sabe que "la cuenta no existe" (`ACCOUNT_NOT_FOUND`); que eso se traduzca en un 404 HTTP es una decisión del protocolo de comunicación. Separarlo en un fichero propio lo hace auditable y extensible sin tocar ni el core ni los routers.

**Impacto en negocio**: determina el código que recibe el cliente del dashboard ante cada tipo de error. Un 404 da información diferente a un 409 o un 500 al cliente para decidir si reintentar, mostrar un mensaje de "no encontrado" o reportar un error del sistema.

### `adapters/api/routes/catalog.py`

**Qué hace**: define los dos endpoints del catálogo y los DTOs Pydantic para sus respuestas.

#### DTOs

| Clase | Tipo | `extra="forbid"` | Propósito |
|---|---|---|---|
| `BuildingItem` | Item individual | No (abierto) | Extensible para añadir `levels`, `cost`, `build_time_s` en el futuro sin romper contrato |
| `BuildingsCatalogResponse` | Wrapper | Sí (cerrado) | Respuesta estable del endpoint; no se prevé extensión |
| `TroopItem` | Item individual | No (abierto) | Extensible para añadir `attack`, `defense`, `speed`, `carry` en el futuro |
| `TroopsCatalogResponse` | Wrapper | Sí (cerrado) | Respuesta estable del endpoint |

El campo `language: dict[str, str]` de cada item lleva exactamente una entrada: `{idioma_realmente_servido: nombre}`. La clave puede diferir del idioma pedido cuando aplica el fallback granular.

#### `get_buildings_catalog`

Endpoint `GET /catalog/buildings`. Delega en `translation_port.get_all_buildings(lang)` para obtener la lista cruda con `lang_servido` por item, luego construye los `BuildingItem` con el campo `language` correcto.

No lanza excepciones propias: `get_all_buildings` nunca falla (fallback total garantizado).

#### `get_troops_catalog`

Endpoint `GET /catalog/troops/{tribe}`. FastAPI valida `tribe` contra el enum `Tribe` automáticamente (422 si es inválido). Si la tribu es válida en el enum pero no tiene tropas en el catálogo, `TroopNotFoundError` se atrapa localmente y se convierte en 404 con un `detail` legible.

**Nota de implementación**: el `404` para tribu sin tropas lo gestiona el router directamente con `HTTPException` (no pasa por el exception handler global de `TravianBotError`). El `detail` del 404 está en español fijo (no localizado) porque la condición es un error de catálogo incompleto, no un error de negocio habitual. Ver divergencia DEV-02 abajo.

**Por qué existen estos endpoints**: el dashboard necesita mostrar nombres de edificios y tropas en el idioma del operador para que la interfaz sea comprensible. El backend es la fuente de verdad del dominio de Travian (los gids y las posiciones de tropas no cambian con el idioma), así que la traducción de esos datos le corresponde al backend.

**Impacto en negocio**: regla de negocio 10 del spec — los nombres traducidos son para mostrar al humano. NUNCA se usan para localizar elementos en el browser de Travian; los selectores del browser siempre usan gids o atributos HTML.

### `adapters/api/dependencies.py` — Cambios en `get_language`

**Qué cambió**: `SUPPORTED_LANGUAGES` ya no se define aquí; se importa de `core/i18n/languages.py`. Además se añadió la dependencia `get_translation_port`.

**`get_language`** ahora declara `accept_language: str | None = Header(default=None, alias="Accept-Language")`. El `default=None` es intencional: hace que FastAPI no rechace la request con 422 cuando el header falta. En ese caso el propio `get_language` lanza HTTP 400 con un mensaje descriptivo.

**`get_translation_port`**: dependencia nueva que recupera el singleton `TranslationPort` de `app.state`. Solo existe para que los routers puedan inyectar el adaptador sin importarlo directamente.

---

### `adapters/api/main.py` — Cambios importantes

#### Lifespan (en vez de `@app.on_event`)

El adaptador se inicializa en un `@asynccontextmanager` llamado `lifespan`, registrado en `FastAPI(lifespan=lifespan)`. Esta es la forma correcta en FastAPI moderno (>= 0.93): `@app.on_event("startup")` está deprecado. Ver divergencia IMPL-01 más abajo.

El adaptador queda en `app.state.translation_port` como singleton, compartido por todos los handlers.

#### Middleware de cabeceras de seguridad (`add_security_headers`)

Se ejecuta en cada request. Añade:
- `X-Request-ID`: reutiliza el de la request si llega, genera UUID v4 si no.
- `X-API-Version`: `0.1.0` (leído de `app.version`).
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- Garantiza `charset=utf-8` en `Content-Type: application/json`.

`Cache-Control` no lo añade este middleware: lo gestiona el segundo middleware solo para rutas de catálogo.

#### Middleware de Cache-Control (`add_catalog_cache_control`)

Añade `Cache-Control: public, max-age=3600` solo a respuestas 2xx de rutas que empiecen por `/catalog/`. No contamina respuestas de error ni otros endpoints.

#### Exception handler global (`travian_bot_error_handler`)

Captura cualquier `TravianBotError` en toda la aplicación. Flujo:

1. `_extract_lang(request)` obtiene el idioma (con fallback silencioso a `es` si el header falta o es inválido).
2. `request.app.state.translation_port.get_message(exc.error_code, lang, **exc.params)` traduce el mensaje.
3. `ERROR_HTTP_MAP.get(exc.error_code, DEFAULT_ERROR_STATUS)` determina el HTTP status.
4. Si `X-Verbose: true` → incluye `error_details` con traza enmascarada.
5. Devuelve `JSONResponse` con `Content-Type: application/json; charset=utf-8`.

Las cabeceras mínimas (`X-Request-ID`, `X-API-Version`, etc.) las añade el middleware de seguridad sobre la respuesta del handler.

#### Enmascarado de datos sensibles en modo verbose

Función `_mask_frame_locals(local_vars)`: enmascara variables locales de cada frame antes de incluirlas en la traza verbose. Tres reglas:

1. Nombre de variable coincide con `password|token|api_key|authorization` (regex case-insensitive) → `"***REDACTED***"`.
2. Nombre de variable coincide con `user_data_dir|profile_dir` → `"***REDACTED***"`.
3. Valor (como string) contiene un dominio de Travian (regex `travian\.(com|es|de|net|ru|org|...)`) → `"***REDACTED***"`.

Las reglas 2 y 3 son una condición obligatoria del `guardian-antideteccion` (sección 11 del spec): un volcado verbose nunca debe revelar la ruta del perfil de Chrome ni el servidor de Travian que opera el bot.

**Por qué existe `_extract_lang` separada de `get_language`**: `get_language` es una dependencia de FastAPI que lanza `HTTPException` cuando el header falta. El exception handler no puede depender de una dependencia que lanza excepciones (crearía recursión). `_extract_lang` tiene la misma lógica de normalización pero con fallback silencioso.

## Catálogos JSON

### Estado real del catálogo (verificado en código)

| Catálogo | es | en | de | fr | ru |
|---|---|---|---|---|---|
| `buildings.json` (40 edificios) | Completo | Completo | **Completo** | **Completo** | **Completo** |
| `troops.json` (50 tropas, 5 tribus x 10) | Completo | Completo | Vacío `""` | Vacío `""` | Vacío `""` |
| `messages.json` (12 códigos) | Completo | Completo | Parcial (solo `ACCOUNT_NOT_FOUND`) | Parcial (solo `ACCOUNT_NOT_FOUND`) | Parcial (solo `ACCOUNT_NOT_FOUND`) |
| Overrides (3 archivos) | `{}` vacíos | — | — | — | — |

### Comportamiento de fallback resultante

- Consulta de edificios en `de`, `fr` o `ru`: **todos los nombres en el idioma pedido** (catálogo completo).
- Consulta de tropas en `de`, `fr` o `ru`: **todos los nombres caen a `es`** (campo `de`/`fr`/`ru` = `""` en todos los items).
- Mensaje de error en `de`/`fr`/`ru`: cae a `es` excepto `ACCOUNT_NOT_FOUND` que tiene traducción.

## Divergencias código/spec detectadas

### IMPL-01 — lifespan en vez de `@app.on_event("startup")`

**Spec** (sección 13, trade-off T-6): menciona `@app.on_event("startup")` como alternativa comparada con `app.state`.

**Código real**: usa `@asynccontextmanager` con `lifespan` registrado en `FastAPI(lifespan=lifespan)`.

**Evaluación**: no es una divergencia problemática. `@app.on_event` está deprecado en FastAPI >= 0.93; `lifespan` es la forma recomendada. El comportamiento es idéntico: el adaptador se inicializa una vez al startup. El spec menciona `on_event` como referencia de la decisión de diseño (singleton en startup), no como mandato de API. **Documentado, no es un defecto.**

---

### SPEC-01 — Catálogo de edificios completo en de/fr/ru (spec decía vacío/parcial)

**Spec** (sección 3, fuera del alcance): "Traducciones de `de`, `fr`, `ru` con contenido real (se declaran como soportados pero con catálogo vacío/parcial — caen a fallback `es`)".

**Código real**: el catálogo base de edificios tiene las 5 traducciones completas (es, en, de, fr, ru) para los 40 edificios. El spec declaraba esto fuera del alcance, pero la implementación lo incluyó igualmente.

**Evaluación**: la implementación va más allá del spec en este punto. El comportamiento es correcto y beneficioso. El fallback que el spec preveía para edificios en de/fr/ru de hecho no aplica (el catálogo está completo). **Registrado como mejora no planificada, no como defecto.**

---

### SPEC-02 — Tropas solo con es/en (alineado con spec)

**Spec**: declaraba tropas en de/fr/ru con catálogo vacío (fuera del alcance).

**Código real**: confirmado — todas las 50 entradas de tropas tienen `"de": ""`, `"fr": ""`, `"ru": ""`. Las consultas de tropas en cualquier idioma distinto de es/en caen al fallback `es`. **Coherente con el spec.**

---

### IMPL-02 — `Accept-Language` declarado como opcional para devolver 400 (no 422)

**Spec** (sección 8): el header `Accept-Language` debe ser obligatorio y devolver 400 cuando falta.

**Código real**: en `get_language`, el header se declara `Header(default=None)` (opcional a nivel FastAPI) para que FastAPI no genere el 422 automático. La validación de ausencia la hace el propio código de `get_language`, que lanza HTTP 400. Esto es exactamente lo que el spec exige (400, no 422), pero el mecanismo es el contrario al intuitivo: se declara opcional para poder devolver el error correcto.

**Evaluación**: la implementación es correcta y el spec lo anticipaba ("Se declara como opcional... para que FastAPI no devuelva 422 cuando el header falta"). La nota en el código documenta el porqué. **Sin divergencia real; registrado para claridad.**

---

### IMPL-03 — 404 de tribu sin tropas usa `detail` en español fijo (no localizado)

**Spec** (sección 5, flujo 2): el error de tribu sin tropas se muestra como 404 con mensaje del catálogo.

**Código real**: en `get_troops_catalog`, cuando `TroopNotFoundError` se lanza por tribu sin tropas, el router lo convierte en `HTTPException(404)` con `detail` hardcodeado en español: `"No hay tropas definidas para la tribu '{tribe.value}' en el catálogo"`. No pasa por `get_message` ni por el exception handler global.

**Evaluación**: el mensaje no está localizado en este caso puntual. La condición (tribu válida pero sin tropas en catálogo) es un error de catálogo incompleto, no un error de negocio habitual que el usuario vaya a ver en producción. **Registrado como divergencia menor; candidato a corrección si el multilenguaje de este error llega a ser relevante.**
